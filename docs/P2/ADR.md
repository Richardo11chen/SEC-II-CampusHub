# ADR

# **ADR-001：采用单体分层架构而非微服务或事件驱动架构**

## **状态**

已接受

## **背景**

CampusHub 项目开发周期为 10 周，团队规模 4 人（均为 Web 开发初学者，重度依赖 AI 辅助），总工时约 240 人时。需要实现用户管理、需求发布、订单流程、评价信用、消息通知等模块。存在可选扩展功能如智能推荐和即时通讯。面临架构选型决策：单体分层、微服务、事件驱动或纯 MVC。

## **决策**

我们决定采用 **前后端分离 + 后端经典三层架构（表现层/Controller、业务层/Service、持久层/Repository）**，并以单体应用形式部署。

## **理由**

- **时间约束**：10 周内需交付可运行系统。微服务需要服务注册、配置中心、API 网关、分布式事务等基础设施，仅搭建环境需 2-3 周；事件驱动需要消息队列、幂等处理、死信队列等，学习曲线陡峭。分层架构零额外基础设施成本。
- **团队能力**：成员仅有 C/C++/Java/Python 入门基础，未接触 Web 开发。分层架构概念简单（关注点分离），与 OOP 思想契合，2 天内可理解并应用。
- **AI 辅助效率**：分层架构为 AI 提供清晰的“上下文边界”，可独立生成 Controller、Service、Repository 代码，互不干扰。AI 对 CRUD 及状态机代码生成准确率极高。
- **功能适配性**：项目核心为 CRUD + 订单状态机 + 信用分计算，无高并发、跨服务事务等分布式需求，单体完全满足。
- **可扩展性**：未来若用户量增长，可将订单模块拆分为独立微服务，当前架构不阻碍演进。

## **后果**

- **正面影响**：开发效率高，调试简单（进程内调用），部署方便（单一进程），团队分工清晰（可垂直按模块或水平按层分工）。
- **负面影响**：单体应用可能随着代码增长变得臃肿，但 10 周规模（约 5000~8000 行后端代码）完全可控；无法独立扩展单个模块，但校园场景并发量低，单实例足够。
- **需要关注的风险**：需严格实施分层依赖（Controller→Service→Repository），避免循环依赖和“泥潭”反模式。通过代码审查和 TypeScript 接口约束来防范。

## **AI 辅助记录**

- **AI 初稿内容摘要**：AI 推荐分层架构，从开发复杂度、可维护性、可扩展性、性能、学习成本、10 周可行性六个维度对比四种架构，给出具体模块划分和依赖关系。
- **人工修订内容**：补充了“可扩展性”中未来拆分为微服务的演进路径；增加了“风险”项中关于循环依赖的防范措施。
- **修订理由**：使决策更完整，明确承认单体架构的局限性并给出缓解措施，符合工程决策的诚实性要求。

# **ADR-002：全栈 TypeScript 及 React + Express 技术栈**

## **状态**

已接受

## **背景**

团队技术基础较弱，仅有 C/C++/Java/Python 入门经验，无 Web 开发背景。需要选择一套前后端技术栈，要求学习曲线平缓、AI 辅助代码生成准确率高、能够快速搭建完整功能。项目要求前后端分离。

## **决策**

我们决定采用 **全栈 TypeScript**，前端使用 **React 18 + Vite**，后端使用 **Express 5 + TypeScript**。

## **理由**

- **语言统一**：前后端均为 TypeScript，可共享类型定义（如 API 请求/响应接口），减少沟通成本，提升协作效率。
- **AI 友好**：React 和 Express 是 AI 训练数据中最常见的框架，Copilot、ChatGPT 等对它们的代码生成准确率极高，尤其适合重度依赖 AI 的团队。
- **学习成本**：JavaScript/TypeScript 语法与 C/Java 相似，团队 1 周内可掌握基本语法；React 组件模型和 Express 中间件模式简单直观。
- **构建工具**：Vite 提供极快的热更新，提升前端调试体验，且配置简单。
- **生态丰富**：npm 拥有海量库（JWT、bcrypt、Zod、Prisma、[Socket.io](https://socket.io/) 等），可快速集成所需功能。

## **后果**

- **正面影响**：开发效率高，类型安全减少运行时错误；前后端可并行开发（通过共享 API 接口定义）；社区活跃，问题容易找到解决方案。
- **负面影响**：TypeScript 需要编译步骤（但 Vite 和 ts-node 可绕过）；回调地狱（通过 async/await 解决）；Express 本身较为轻量，缺少内置分层约束（需团队自行约定）。
- **需要关注的风险**：团队可能写出“意大利面代码”，需通过架构规范（分层）和代码审查强制约束。另外 Node.js 单线程模型需注意阻塞操作（使用异步 I/O）。

## **AI 辅助记录**

- **AI 初稿内容摘要**：AI 根据需求文档推荐全栈 TypeScript + React + Express，并给出了每个框架的优缺点对比。
- **人工修订内容**：增加了“语言统一带来的类型共享优势”和“Node.js 单线程风险提示”。
- **修订理由**：突出 TypeScript 相比纯 JS 的核心价值（类型共享），并提醒团队注意 Node.js 的性能特性，避免因未使用 worker_threads 而阻塞。

# **ADR-003：选用 MySQL 数据库及 Prisma ORM**

## **状态**

已接受

## **背景**

系统需要存储用户、需求、订单、评价、消息等关系型数据，且订单状态流转需要事务保证，信用分计算涉及多表更新。需要选择数据库及访问层，要求开发便捷、类型安全、AI 辅助友好。

## **决策**

我们决定使用 My**SQL** 作为数据库，**Prisma** 作为 ORM 和数据访问工具。

## **理由**

- **数据库选型**：MySQL 完全支持 ACID 事务，满足订单和信用分一致性需求；支持 JSON 字段，便于存储需求的扩展属性（如地理位置、自定义字段）
- **ORM 选型**：Prisma 提供声明式 Schema，可从模型自动生成 TypeScript 类型，实现端到端类型安全；迁移功能简单（prisma migrate dev），AI 可根据需求自动生成模型定义和迁移文件；相比手写 SQL 或 MyBatis，Prisma 对新人更友好，避免 SQL 注入风险。
- **AI 效率**：Prisma Schema 结构清晰，AI 可准确生成模型关系（1:N, N:N）及复杂查询，减少手写联表错误。

## **后果**

- **正面影响**：开发速度快，类型安全减少运行时数据库错误；迁移文件可版本控制，便于团队协作；Prisma Studio 提供可视化数据浏览，方便调试。
- **负面影响**：Prisma 对复杂查询（如多表聚合）的语法不如原生 SQL 直观，但可通过 $queryRaw 回退；学习 Prisma 特有语法（约半天即可上手）；PostgreSQL 相比 MySQL 增加少量运维认知成本。
- **需要关注的风险**：Prisma 在某些边缘场景（如嵌套事务）行为与预期不符，需充分测试。另外，PostgreSQL 默认隔离级别为 Read Committed，需注意并发抢单场景下的丢失更新（已通过乐观锁解决）。

## **AI 辅助记录**

- **AI 初稿内容摘要**：AI 推荐 PostgreSQL + Prisma，并生成了示例 Schema 和查询代码。
- **人工修订内容**：根据团队成员常用偏好改为MySQL；删除了 AI 建议的 MongoDB 选项。
- **修订理由**：明确 Prisma 的边界和应对策略，避免团队盲目依赖 ORM 导致复杂查询效率低下；同时排除非关系型数据库，因为项目事务需求明确。

# **ADR-004：使用 JWT + bcrypt 进行无状态认证**

## **状态**

已接受

## **背景**

系统需要实现用户注册、登录、登出及权限控制。非功能需求要求密码加密存储，防止常见攻击。团队需要简单、可扩展且对前后端分离友好的认证方案。

## **决策**

我们决定采用 **JWT（JSON Web Token）** 作为认证令牌，使用 **bcrypt** 进行密码哈希，令牌放在 HTTP 请求头 Authorization: Bearer <token> 中。

## **理由**

- **无状态**：后端无需存储会话信息，便于水平扩展（未来若增加多实例，无需共享 Session 存储）。
- **前后端分离**：JWT 天然适合 SPA，前端存储（localStorage/sessionStorage）简单，每次请求自动携带。
- **安全基线**：bcrypt 内置盐和自适应哈希，抵抗彩虹表攻击，满足项目安全需求。
- **实现简单**：jsonwebtoken 和 bcrypt 库成熟，AI 可生成完整中间件（登录签发、验证拦截）。
- **角色集成**：可将用户角色（普通用户/管理员）编码进 JWT 负载，方便实现后台管理的授权。

## **后果**

- **正面影响**：开发快速，无状态便于调试和部署；可轻松实现登出（前端删除令牌即可，也可辅助维护 JWT 黑名单）。
- **负面影响**：JWT 一旦签发在有效期内无法主动失效（除非使用黑名单），存在令牌被盗用风险。解决方案：设置较短有效期（如 7 天），并提供刷新令牌；或对敏感操作用额外密码验证。
- **需要关注的风险**：必须使用 HTTPS 防止令牌在传输中被截获；前端存储需考虑 XSS 攻击（建议使用 httpOnly cookie 更安全，但增加了 CSRF 防护）。本项目采用 localStorage，需加强 XSS 过滤（Zod 校验 + 输出转义）。

## **AI 辅助记录**

- **AI 初稿内容摘要**：AI 给出了 JWT 生成与验证的中间件代码示例，以及 bcrypt 加密对比。
- **人工修订内容**：增加了“JWT 主动失效问题的解决方案（短有效期、刷新令牌、黑名单）”；增加了“XSS 防范建议”。
- **修订理由**：AI 默认 JWT 完美无缺，但实际工程中需考虑令牌撤销场景，补充后使决策更严谨，符合课程对安全性的要求。
