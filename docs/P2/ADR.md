# ADR

# **ADR-001：采用分层架构（设计阶段）→ 双微服务（实现阶段）**

## **状态**

已接受（设计为单体分层架构，实现阶段演化为双微服务）

## **背景**

CampusHub 项目开发周期为 10 周，团队规模 4 人（均为 Web 开发初学者，重度依赖 AI 辅助），总工时约 240 人时。需要实现用户管理、需求发布、订单流程、评价信用、消息通知等模块。面临架构选型决策：单体分层、微服务、事件驱动或纯 MVC。

## **初始决策（P2 设计阶段）**

设计阶段决定采用 **前后端分离 + 后端经典三层架构（表现层/Controller、业务层/Service、持久层/Repository）**，并以单体应用形式部署。

### 理由（设计阶段）
- **时间约束**：10 周内需交付可运行系统。微服务需要服务注册、配置中心、API 网关、分布式事务等基础设施，仅搭建环境需 2-3 周。
- **团队能力**：成员仅有 C/C++/Java/Python 入门基础，未接触 Web 开发。分层架构概念简单，2 天内可理解并应用。
- **AI 辅助效率**：分层架构为 AI 提供清晰的"上下文边界"，可独立生成 Controller、Service、Repository 代码。
- **功能适配性**：项目核心为 CRUD + 订单状态机 + 信用分计算，无高并发、跨服务事务需求。

## **实际演化（P3/P4 实现阶段）**

实际实现为 **双微服务架构**，通过 npm workspaces 管理：

| 包名 | 端口 | 职责 | 开发者 |
|------|------|------|--------|
| `@campushub/service-a` | 3001 | 需求 CRUD + 订单生命周期 | 陈奕澎 |
| `@campushub/service-b` | 3002 | 认证 + 用户 + 评价 + 通知 + 消息 + 管理 + 上传 | 张少逸 |
| `@campushub/shared` | — | Prisma 客户端 + Repository + 中间件 + 工具类 | 共享 |

### 演化理由
- **分工独立**：两人并行开发各自后端服务，互不阻塞，本地可独立启动调试。
- **共享包**：将 Prisma schema、Repository、中间件提取为 shared 包编译产物，避免代码重复。
- **模块边界清晰**：需求/订单与用户/认证天然独立，拆分后改动范围小。
- **Monorepo 管理**：npm workspaces 统一管理三个包，简化构建和依赖。

## **后果**

- **正面**：并行开发效率高，服务独立重启；shared 包强制关注点分离。
- **负面**：服务间无法共享内存状态；修改 shared 包后需重新编译（`npx tsc`），否则不生效。
- **保持正确**：每个服务内部严格三层架构（Controller→Service→Repository）；乐观锁处理并发；无分布式事务需求。

## **AI 辅助记录**

- **AI 初稿内容摘要**：AI 推荐分层架构，从六个维度对比四种架构。
- **人工修订内容**：补充了"实际演化为微服务"的说明；增加了"共享包编译注意事项"。
- **修订理由**：诚实反映架构决策的变化过程。

# **ADR-002：全栈 TypeScript 及 React + Express 技术栈**

## **状态**

已接受

## **背景**

团队技术基础较弱，仅有 C/C++/Java/Python 入门经验，无 Web 开发背景。需要选择一套前后端技术栈，要求学习曲线平缓、AI 辅助代码生成准确率高、能够快速搭建完整功能。项目要求前后端分离。

## **决策**

我们决定采用 **全栈 TypeScript**，前端使用 **React 18 + Vite**，后端使用 **Express 5 + TypeScript**。

## **理由**

- **语言统一**：前后端均为 TypeScript，可共享类型定义（如 API 请求/响应接口），减少沟通成本。
- **AI 友好**：React 和 Express 是 AI 训练数据中最常见的框架，代码生成准确率极高。
- **学习成本**：JavaScript/TypeScript 语法与 C/Java 相似，团队 1 周内可掌握基本语法。
- **构建工具**：Vite 提供极快的热更新，提升前端调试体验。
- **生态丰富**：npm 拥有海量库（JWT、bcrypt、Zod、Prisma 等），可快速集成所需功能。

## **后果**

- **正面**：开发效率高，类型安全减少运行时错误；前后端可并行开发。
- **负面**：TypeScript 需要编译步骤（Vite 和 tsx 可绕过）；Express 缺少内置分层约束（需团队自行约定）。
- **风险**：团队可能写出"意大利面代码"，需通过架构规范（分层）和代码审查强制约束。Node.js 单线程模型需注意阻塞操作。

## **AI 辅助记录**

- **AI 初稿内容摘要**：AI 推荐全栈 TypeScript + React + Express，给出了各框架优缺点对比。
- **人工修订内容**：增加了"语言统一带来的类型共享优势"和"Node.js 单线程风险提示"。
- **修订理由**：突出 TypeScript 相比纯 JS 的核心价值，并提醒团队注意 Node.js 的性能特性。

# **ADR-003：选用 MySQL 8.0 数据库及 Prisma ORM**

## **状态**

已接受

## **背景**

系统需要存储用户、需求、订单、评价、消息等关系型数据，且订单状态流转需要事务保证，信用分计算涉及多表更新。需要选择数据库及访问层，要求开发便捷、类型安全、AI 辅助友好。

## **决策**

使用 **MySQL 8.0** 作为数据库，**Prisma** 作为 ORM。

## **理由**

- **数据库选型**：MySQL 完全支持 ACID 事务，满足订单和信用分一致性需求；InnoDB 引擎成熟稳定。
- **ORM 选型**：Prisma 提供声明式 Schema，从模型自动生成 TypeScript 类型，实现端到端类型安全；迁移功能简单（`prisma migrate dev`）。
- **AI 效率**：Prisma Schema 结构清晰，AI 可准确生成模型关系及复杂查询。

## **后果**

- **正面**：开发速度快，类型安全减少运行时数据库错误；迁移文件可版本控制。
- **负面**：Prisma 对复杂查询（如多表聚合）的语法不如原生 SQL 直观，但可通过 `$queryRaw` 回退。
- **风险**：Prisma 在某些边缘场景（如嵌套事务）行为与预期不符，需充分测试。MySQL 默认隔离级别为 Read Committed，并发抢单场景下的丢失更新通过乐观锁解决。

## **AI 辅助记录**

- **AI 初稿内容摘要**：AI 推荐 PostgreSQL + Prisma，并生成了示例 Schema 和查询代码。
- **人工修订内容**：根据团队成员常用偏好改为 MySQL；删除了 AI 建议的 MongoDB 选项。
- **修订理由**：明确 Prisma 的边界和应对策略，避免团队盲目依赖 ORM。

# **ADR-004：使用 JWT + bcrypt 进行无状态认证（Refresh Token 轮转，MySQL 存储）**

## **状态**

已接受

## **背景**

系统需要实现用户注册、登录、登出及权限控制。非功能需求要求密码加密存储，防止常见攻击。

## **决策**

采用 **JWT（JSON Web Token）** 作为认证令牌，使用 **bcrypt** 进行密码哈希，Refresh Token 在 MySQL 中存储和撤销。

## **关键设计**

- **双令牌机制**：Access Token（有效期 3600 秒）+ Refresh Token（有效期 7 天，轮转策略：每次刷新时旧令牌失效并签发新令牌）。
- **登出实现**：将 Refresh Token 标记为已撤销（`isRevoked=true`），**不使用 Redis 黑名单**。
- **密码加密**：bcrypt（salt rounds=10），单向哈希。
- **速率限制**：登录 20/min、注册 10/min、刷新 30/min，防止暴力破解。

## **理由**

- **无状态**：后端无需存储会话信息，便于水平扩展。
- **安全基线**：bcrypt 内置盐和自适应哈希，抵抗彩虹表攻击。
- **实现简单**：`jsonwebtoken` 和 `bcrypt` 库成熟，AI 可生成完整认证流程。
- **角色集成**：用户角色（student/admin）编码进 JWT 负载，方便权限校验。

## **后果**

- **正面**：开发快速，无状态便于调试和部署；Refresh Token 轮转提高安全性。
- **负面**：JWT 在有效期内无法主动撤销（需等待过期）。解决方案是设置短有效期 + Refresh Token 轮转 + MySQL 撤销标记。
- **风险**：必须使用 HTTPS 防止令牌被截获；前端 localStorage 存储需防范 XSS（Zod 校验 + 输出转义）。

## **AI 辅助记录**

- **AI 初稿内容摘要**：AI 给出了 JWT 生成与验证的中间件代码示例，以及 bcrypt 加密对比。
- **人工修订内容**：增加了"JWT 主动失效问题的解决方案（短有效期、刷新令牌、MySQL 撤销）"；增加了"XSS 防范建议"。
- **修订理由**：使决策更严谨，符合课程对安全性的要求。

# **ADR-005：使用 optimistic locking（乐观锁）处理并发抢单**

## **状态**

已接受

## **背景**

多个学生可能同时点击"接单"按钮承接同一个需求。需要防止"一需求多接"的并发问题。

## **决策**

在 Demand 和 Order 表上引入 `version` 整数字段（默认 1），每次更新时通过 `updateMany` + `version` 匹配实现乐观锁。更新时将 `version` 加 1，如果 `affectedRows === 0` 则说明数据已被其他请求修改，返回 HTTP 409 冲突错误。

## **理由**

- **无需外部中间件**：乐观锁只需要数据库的一个整数列，无需 Redis 分布式锁或消息队列。
- **适用场景匹配**：抢单冲突概率低（校园场景并发量小），乐观锁的重试成本很低。
- **Prisma 友好**：`updateMany` 的 `where` 条件天然支持 version 匹配。

## **后果**

- **正面**：实现简单可靠，零额外基础设施；冲突时用户刷新页面即可重试。
- **负面**：高并发下冲突率升高会导致更多重试，但校园场景不会出现此问题。

## **AI 辅助记录**

- **AI 初稿内容摘要**：AI 给出了 Prisma 中使用乐观锁的代码示例。
- **人工修订内容**：增加了"冲突后的用户体验说明"（提示用户刷新）。
- **修订理由**：明确乐观锁在本项目中的适用边界。
