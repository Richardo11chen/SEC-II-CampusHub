# 架构设计文档

# 架构概览

基于选定的**前后端分离 + 后端经典三层（表现层/业务层/持久层）分层架构**，并演化为**双微服务部署模式**，以下提供完整的架构概览和架构图。

CampusHub采用**B/S模式**，前端为单页应用（React 18），后端拆分为两个 Express 服务（Service-A 处理需求与订单，Service-B 处理用户/认证/评价/通知/管理），前后端通过HTTP RESTful API通信。两个服务共享 `@campushub/shared` 基础设施包（Prisma 客户端、JWT 工具、中间件、Repository 层）。后端内部严格划分为三个逻辑层：

- **表现层（Controller）**：接收请求、参数校验（Zod）、响应封装（统一 `code/message/data` 格式）、异常处理。
- **业务层（Service）**：实现订单状态机、信用分计算、爽约惩罚逻辑、通知触发等核心业务。
- **持久层（Repository/DAO）**：封装数据库CRUD，使用 Prisma ORM，通过乐观锁（version 字段）处理并发。

辅助模块包括**基础设施**（JWT/bcrypt 认证、AES-256-CBC 电话加密、文件上传、通知推送、定时任务清理）和**MySQL 8.0 数据库**。

# 模块划分

## **模块划分与职责边界**

### **1. 前端模块（Frontend）**

- **职责**：提供用户交互界面，发送HTTP请求到后端API，展示数据。
- **子模块**：
    - 用户界面（登录/注册、个人资料）
    - 需求界面（发布、列表、详情、筛选）
    - 订单界面（接单、确认完成、历史记录）
    - 评价界面（评分、评价展示）
    - 消息界面（通知列表、即时通讯聊天）
    - 管理后台界面（用户管理、需求审核、统计看板）
- **技术实现**：React 18 + TypeScript + Vite

### **2. 后端 Service-A 模块（端口 3001）—— 需求与订单**

负责需求发布浏览和订单生命周期管理。

**表现层（Controller）**：
- DemandController：发布需求、获取列表/详情/筛选、更新、删除
- OrderController：接单、更新订单状态、获取订单历史/详情、取消订单、发起纠纷

**业务层（Service）**：
- DemandService：需求发布校验（信用分≥40）、列表查询（含筛选排序+全文搜索）、乐观锁并发控制
- OrderService：订单状态机流转、乐观锁防并发抢单、爽约判定与信用扣分、30天累计爽约≥3次冻结接单15天、通知触发

**路由层**：RESTful 路由挂载在 `/api/demands` 和 `/api/orders` 下

### **3. 后端 Service-B 模块（端口 3002）—— 用户/认证/评价/通知/管理**

负责用户体系、认证授权、评价信用、通知消息和管理后台。

**表现层（Controller）**：
- AuthController：注册、登录、登出、刷新令牌
- UserController：获取/更新个人资料、获取他人公开资料
- ReviewController：提交评价、查看自己某订单的评价
- NotificationController：获取通知列表、标记已读
- MessageController：发送/获取订单聊天消息
- AdminController：用户管理、需求审核、纠纷处理、管理员申请审批、数据统计
- UploadController：文件上传（头像/需求图片/证据）

**业务层（Service）**：
- AuthService：JWT 签发验证、refresh token 轮转、bcrypt 密码哈希
- UserService：资料更新（含 AES 电话加密）、脱敏展示、信用分查询
- ReviewService：评分提交、信用分更新（CREDIT_DELTA 映射表：5→+3, 4→+1, 3→0, 2→-5, 1→-5）
- NotificationService：站内信通知的创建与查询
- MessageService：聊天消息的存储与查询
- AdminService：用户封禁/启用、需求下架、纠纷裁决、管理员申请审批、统计看板
- UploadService：文件存储（本地/OSS）

### **4. 共享基础设施包（@campushub/shared）**

两个服务共同依赖的代码包，包含：

- **Prisma 客户端**：数据库模型定义与 ORM 操作
- **Repository 层**：user-repository, demand-repository, order-repository, review-repository, notification-repository, message-repository, dispute-repository, refresh-token-repository, no-show-record-repository, demand-image-repository
- **中间件**：JWT 认证中间件、管理员权限校验、速率限制（limiter：登录20/min、注册10/min、刷新30/min、订单60/min、通用100/min）、错误处理中间件、Zod 校验中间件
- **工具类**：JWT 生成/验证、bcrypt 加密/对比、AES-256-CBC 电话加解密、统一响应格式（successResponse/createdResponse/paginatedResponse/errorResponse）、自定义错误类（NotFoundError/ForbiddenError/ConflictError/BadRequestError）
- **通知辅助**：notifyOrderTaken / notifyOrderCompleted / notifyOrderConfirmed / notifyOrderCancelled / notifyReviewReceived

### **5. 数据库模块（Database）**

- **数据库**：MySQL 8.0（InnoDB 引擎）
- **ORM**：Prisma ORM（类型安全、自动迁移）
- **表**：User, Demand, DemandImage, Order, Review, Notification, Message, Dispute, AdminApplication, RefreshToken, NoShowRecord, FieldModificationLog（共 12 张表）
- **核心约束**：Order.demandId UNIQUE（一需求一订单）、version 乐观锁字段、credit_score CHECK(0-100)、rating CHECK(1-5)

### **6. 基础设施模块（Infrastructure）**

- **JWT 认证**：Access Token（3600s）+ Refresh Token（7天轮转，MySQL 存储撤销）
- **密码加密**：bcrypt（salt rounds=10）
- **电话加密**：AES-256-CBC 加密存储为 VARBINARY(255)
- **文件存储**：本地文件系统（multer），支持头像/需求图片/证据图片
- **速率限制**：express-rate-limit，按接口分级配置
- **定时任务**：node-schedule，每日凌晨 3 点清理超过 30 天的开放需求
- **日志**：Winston（分级日志）+ Morgan（HTTP 请求日志）

## 技术选型

| **层次** | **实际选择** | **选择理由** |
| --- | --- | --- |
| **前端框架** | React 18 + TypeScript (Vite) | • 生态成熟，组件化开发效率高• TypeScript 类型安全• Vite 热更新极快 |
| **后端框架** | Express 5 + TypeScript | • 轻量灵活，中间件生态丰富• 三团队熟悉 JavaScript/TypeScript |
| **数据库** | MySQL 8.0 (InnoDB) | • 关系型数据库，支持事务（订单状态、信用分一致性）• 开源稳定 |
| **ORM** | Prisma | • TypeScript 原生，类型安全• Schema 声明式定义，迁移方便 |
| **认证** | JWT + bcrypt | • 无状态认证，适合前后端分离• Access/Refresh Token 双令牌机制 |
| **参数校验** | Zod | • TypeScript 原生类型推导• 与 Express 集成良好 |
| **日志** | Winston + Morgan | • 分级日志（info/error）• HTTP 请求自动记录 |
| **定时任务** | node-schedule | • 实现每日过期需求清理• 轻量无外部依赖 |
| **部署方式** | Node.js 进程（GitLab CI） | • 双服务独立部署• CI 流水线自动安装→构建→测试 |
| **版本控制** | Git + GitLab | • 多分支并行开发（P0~P4）• CI 集成自动化测试 |

## **架构演进说明**

本项目的架构设计经历了从**单体分层架构**到**双微服务架构**的演进：

- **P2 设计阶段**：按照经典的 MVC+分层架构设计，计划采用单体部署。
- **P3/P4 实现阶段**：实际开发中将后端拆分为两个独立的 Express 服务：
  - **Service-A**（`backend/service-a/`，端口 3001）：需求 + 订单（开发者：陈奕澎）
  - **Service-B**（`backend/service-b/`，端口 3002）：认证 + 用户 + 评价 + 通知 + 消息 + 管理 + 上传（开发者：张少逸）
- **共享包**（`backend/shared/`）：两个服务共享的 Prisma schema、Repository、中间件和工具类，编译为 `@campushub/shared` npm workspace 包。

### 与 P2 架构设计的差异

| 设计项 | P2 计划 | 实际实现 |
|--------|---------|---------|
| **部署模式** | 单体应用 | 双微服务（端口 3001 + 3002） |
| **Redis** | JWT 黑名单 + 热点缓存 | 未使用（撤销 token 写入 MySQL） |
| **Docker** | Docker Compose 部署 | 未使用（Node.js 直接运行） |
| **WebSocket** | P2 即时通讯 | 未实现（消息走 REST API） |
| **推荐系统** | RecommendService + 推荐算法 | 未实现 |
| **信用分服务** | 独立 CreditService | 信用逻辑在 review-service + order-service 中 |
| **48h 自动确认** | node-schedule 定时任务 | 未实现（需求方手动确认） |
| **MySQL 版本** | MySQL 15 | MySQL 8.0 |
| **管理员日志** | admin_log 表 | FieldModificationLog 表 |
