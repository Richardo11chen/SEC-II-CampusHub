### **2. AI 助力分析（Q1）**

**本阶段 AI 最大的贡献是：**

AI 在架构决策过程中提供了多维度的对比分析，帮助我们快速排除不合适的微服务和事件驱动架构，聚焦于分层架构。AI 还能根据需求文档生成具体的模块划分、依赖关系图、接口定义，并给出可直接落地的最佳实践（如乐观锁防并发、48小时自动确认等）。尤其是 ADR 的初稿生成，极大提高了架构文档的撰写效率。

**不同 Prompt 策略下 AI 回答质量的差异：**

我们尝试了四种 prompt 策略（见"架构辩论赛.pdf"中的对话）：

- **策略1（通用提问）**：回答泛泛，无项目针对性。
- **策略2（提供技术背景）**：回答能针对技术栈评估，但业务深度不足。
- **策略3（提供完整需求文档）**：AI 能提取功能列表、MVP范围，分析贴合项目。
- **策略4（角色扮演 + 完整文档）**：回答质量最高，包含技术选型、难点攻坚、AI协作策略和项目节奏。

**结论**：最有效的 prompt 是"扮演架构师 + 提供完整项目背景（需求文档、团队规模、周期、技术能力）"，能让 AI 从信息提供者转变为决策顾问。

### **3. AI 误导分析（Q2）**

**AI 在架构建议中的典型问题：**

- **问题1：过度推荐微服务或事件驱动**
    - **如何发现**：在部分通用 prompt 下，AI 会提及微服务"可扩展性好"，未主动评估项目约束。
    - **如何修正**：我们在 prompt 中明确加入"团队4人、10周、Web初学者、重度依赖AI"，AI 随即调整推荐为分层架构。
- **问题2：技术选型过于理想化**
    - **如何发现**：AI 曾建议使用 Kafka 或 Redis 集群应对"可能的并发高峰"，但这对于校园项目属于过度设计。
    - **如何修正**：人工根据实际并发量（预估 <100 QPS）删除了不必要的中间件，并补充了"可暂不实现"的备注。
- **问题3：忽略安全细节**
    - **如何发现**：AI 在 JWT 方案中未提及令牌撤销问题，也未讨论 XSS 对 localStorage 的影响。
    - **如何修正**：我们在 ADR-004 中人工补充了短有效期、刷新令牌、黑名单方案，并增加 XSS 防范建议。

### **4. Prompt 改进计划（Q3）**

**上阶段（P1 需求分析）提出的改进措施，验证结果：**

- 上阶段措施：要求 AI 在回答前先列出"已知约束条件"再给出建议。
- 验证结果：有效。本阶段我们在 prompt 中主动列出团队规模、周期、技术能力，AI 的回答明显更有针对性。

**本阶段新的改进措施：**

1. **使用角色扮演前缀**：例如"请你扮演一个架构师角色分析我们的项目"，可显著提升回答的专业度和可操作性。
2. **分步提问**：先让 AI 对比架构，再要求细化模块，再要求生成 ADR，避免一次性输出过长导致信息遗漏。
3. **强制 AI 列出"不推荐方案及理由"**：例如明确要求"为什么不选其他三种架构"，帮助团队理解权衡过程。
4. **要求 AI 标注不确定内容**：例如"对于 P2 功能（即时通讯），如果时间不足可回退到短轮询，请标注此风险"。这样可避免盲目跟从。

### **5. 本阶段的核心工程判断**

**决策内容（P2 设计阶段）：**

采用 **前后端分离 + 后端三层分层架构**，技术栈为 **全栈 JavaScript + React + Express + MySQL + Prisma + JWT/bcrypt**，部署使用 **Docker Compose**。模块划分包含 Controller、Service、Repository 三层，明确依赖关系与接口规范，并撰写了 4 条 ADR 记录关键架构决策。

**实现阶段的架构演化说明（P3/P4 更新）：**

实际开发中，我们在保留三层架构设计原则的基础上，将后端拆分为两个独立的 Express 服务：

- **Service-A**（端口 3001）：需求 + 订单（开发者：陈奕澎）
- **Service-B**（端口 3002）：认证 + 用户 + 评价 + 通知 + 消息 + 管理 + 上传（开发者：张少逸）
- **@campushub/shared**：两个服务共享的 Prisma 客户端、Repository、中间件和工具类（npm workspaces 管理）

此外，以下 P2 设计的功能因优先级/时间原因未实现：Redis 缓存、Docker 容器化、WebSocket 即时通讯、智能推荐系统、独立的 CreditService、48 小时自动确认定时任务。详见架构设计文档中的"架构演进说明"。

**为什么 AI 无法做这个决策：**

- **价值权衡无法量化**：AI 可以列出分层架构的优缺点，但无法真正评估"10 周内 4 人团队的交付风险"和"课程评分对架构复杂度的容忍度"。人类需要结合课程要求、团队情绪、技术掌握速度等主观因素做最终判断。
- **非功能需求的优先级排序**：AI 倾向同时满足所有质量属性（高扩展、高安全、高性能），但实际项目中我们主动降低了扩展性要求（放弃微服务）以换取开发速度。这种优先级取舍需要人工决策。
- **团队能力的隐性知识**：AI 不知道每个成员的学习速度、可用时间、既往 bug 修复能力。只有团队自己知道"我们连 Git 分支都用不太熟练"，因此选择最简单的单体架构而非微服务。
- **课程评分标准的解读**：AI 不知道评审老师更看重"完整可运行的系统"还是"炫酷的架构设计"。根据经验判断，10 周内跑通全部 PO 功能比采用微服务得高分更重要。
