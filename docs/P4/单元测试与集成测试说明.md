## 五、集成测试

路径：`backend/__tests__/integration/`

使用 `supertest` 启动 Express app 发真实 HTTP 请求。通过 mock 数据库层来避免对外部 MySQL 的依赖。

### `auth-flow.test.ts`（379 行）

完整认证生命周期：注册 → 登录 → refresh → 获取用户信息 → 登出 → 旧 token 失效。

| 步骤 | 断言 |
|------|------|
| 注册 | 201，返回 masked studentId |
| 登录 | 200，返回 token / refreshToken / expiresIn |
| 获取 `/api/users/me` | 200，返回完整用户信息 |
| refresh token | 200，返回新 token 对 |
| 旧 refreshToken 再次 refresh | 401 |
| logout | 旧 accessToken 访问受保护路由 → 401 |

### `order-flow.test.ts`（504 行）

两个用户的完整订单流程（A=发布者，B=服务方）：

1. A 注册 + 登录 → 创建需求（status=开放）
2. B 注册 + 登录 → 接单（status=进行中）
3. B 提交完成（status=待确认）
4. A 确认完成（status=已完成）
5. A 评价 B 4★ → B 信用分 +1
6. B 评价 A 5★ → A 信用分 +3
7. 重复评价 → 409

### `error-flows.test.ts`（443 行）

两个异常流程：

**流程 1 — 爽约限制接单：**
- A 创建需求 → B 接单 → B 取消（爽约 ×3）
- 第 4 次接单 → 403 "因频繁爽约，您已被限制接单"
- 信用分 70 → 40（3 × 10 分扣减）

**流程 2 — 未认证访问被拒：**
- 无 token 访问受保护端点 → 401（共 5 个端点验证）

## 六、运行方式

```bash
cd backend

# 运行所有测试
npm test

# 监听模式（开发时使用）
npm run test:watch

# 带覆盖率报告
npm run test:coverage

# 运行特定包测试
npx vitest run --project shared
npx vitest run --project service-a
npx vitest run --project service-b

# 运行特定文件
npx vitest run src/__tests__/order-service.test.ts --project service-a
```

## 七、CI/CD 流水线

配置在 `.gitlab/backend.yml`，包含四个阶段：

```
install → lint (tsc --noEmit) → build → test (vitest + 覆盖率)
```

GitLab CI 中使用 MySQL 8.0 service 提供测试数据库，`prisma db push` 初始化 schema 后运行集成测试。测试报告以 JUnit XML 格式上传，覆盖率报告保存为 artifacts。
